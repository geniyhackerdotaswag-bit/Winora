# Winora contributor rules

## Architecture

- Preserve the production dependency graph: `Infrastructure -> Core`, `System -> Core`, `ElevatedHost -> Core + System + Infrastructure`, and `App -> Core + Infrastructure + System`.
- `Winora.Core` stays platform- and serializer-independent. It must not reference WinUI, Windows App SDK, System.Text.Json, the registry, PowerShell, COM, P/Invoke, or concrete file systems.
- `Winora.System` contains documented Windows adapters and never displays UI. `Winora.App` owns every dialog, notification, navigation, and confirmation surface.
- Winora runs elevated. The owner decided this on 2026-08-02, overriding the earlier rule that the main window stays at medium integrity. That rule rested on a claim that turned out to be false: a packaged MSIX app *can* be elevated — launching `shell:AppsFolder\{AUMID}` with the `runas` verb yields a process whose token reports `TokenElevation` non-zero, measured on this machine. The app relaunches itself once at startup when started without rights, and carries on unelevated if the prompt is declined.
- Because the window is elevated, never add arbitrary command execution, never take a path or a command from anything but Winora's own catalog, and treat every deletion guard as load-bearing. `Windows.old` stays refused at every privilege level: no documented programmatic removal, and deleting it closes the route back to the previous Windows version.
- Running elevated costs the whole automated feedback loop, and every one of these was hit for real:
  - A medium-integrity shell cannot stop or close the app. Installing a build over a running one fails with `0x80073D02` until the window is closed by hand.
  - `Add-AppxPackage -Register` refuses a same-version re-register in developer mode (`0x80073CFB`). Bump `Version` in `Package.appxmanifest` to iterate.
  - Registering a *different layout* at the *same version* reports success and silently keeps the old `InstallLocation`. Registering the Release manifest over an already-registered Debug one left the Debug folder installed, marker file and all. Always read back `Get-AppxPackage | Select InstallLocation` after registering, and bump the version when switching layouts.
  - `PrintWindow` against the elevated window returns a blank frame, and UI Automation cannot attach. Screenshots and UIA-driven checks are impossible from a normal session — visual verification depends on the user. Verify behaviour instead through unit tests and external measurement (registry reads, `SystemParametersInfo` reads) from a separate unpackaged process, which still works.
  - Anything under `%LOCALAPPDATA%\Temp` — including scratch scripts — sits inside the folder the cleaner empties, and will be deleted.

## Safety and quality

- Develop behavior test-first. Every mutation must pass through capability probing, immutable dry-run planning, confirmation, verified backup, conditional apply, independent verification, durable journaling, and idempotent rollback.
- Block direct mutation for unknown, unsupported, partial, unavailable, or unsafe capabilities. Never replace external state after fingerprint drift.
- Use documented Windows mechanisms only and include the relevant Microsoft Learn URI next to every mutating adapter.
- **A domain that mutates outside `ChangeCoordinator` must be added to `JournalAllowlist`, or it leaves no trace at all.** The journal admits only allowlisted catalog ids, and `ActionJournalWriter` swallows a rejection on purpose — journalling must never fail a change that already happened. The two combined mean a missing allowlist entry is silent. Measured on 2026-08-07: temporary-file reclamation had been deleting files with no record anywhere since it stopped being a coordinator operation, and nothing failed. Assert the new ids **by name**, not by rebuilding the same expression the code uses; that test passes even when the union is dropped entirely.
- A mechanism you cannot cite a Microsoft Learn URI for ships as `Guided` or `Unsupported` with a stable reason code. It never ships as an unconditional fallback, and a plausible-looking registry value is not documentation.
- Where a Learn page documents a value's *kind* differently from what the live system holds, probe both and degrade to `Unknown`/`Guided` on a mismatch instead of guessing.
- **Resolved on 2026-08-04: the registry domains work, and only from a properly installed signed package.** Verified end to end and from outside the app — the taskbar screen wrote `ShowTaskViewButton` `0 → 1`, an unpackaged PowerShell read `1` back from the real hive, and the journal holds the full chain `Planned → Prepared → BackupCreated → Applying → Applied → Verified → Completed` with a committed backup manifest. The working shape is: sign the MSIX, install it with `Add-AppxPackage <file>.msix` **from an elevated prompt**, and remove any previous dev-mode registration first (an existing unpackaged registration makes the install fail with `0x80073CFB`; a non-elevated install fails with `0x80070005`). `Get-AppxPackage` must then report `SignatureKind: Developer` and an `InstallLocation` under `C:\Program Files\WindowsApps`. **`Add-AppxPackage -Register` on a loose layout does not give you this** — it produces `SignatureKind: None` and the broken behaviour below. Never verify a registry domain against a dev-registered build and conclude it works.
- The history below is why that matters, and it stays here as the reason the rule is not negotiable. On an unsigned build the failure was **asymmetric**, and it caused real data loss on 2026-08-02. `RegistryWriteVirtualization` set to `disabled` needs the `unvirtualizedResources` restricted capability, which Windows does not grant to an unsigned package registered with `Add-AppxPackage -Register`. Measured, both halves on the same unsigned build:
  - **Deleting a value from a key that already exists reaches the real user hive.** Twelve entries the app removed from `HKCU\...\Run` were genuinely gone from the real hive, verified from an unpackaged process.
  - **A key the app creates itself never leaves the container.** `HKCU\Software\Winora\DisabledStartup`, where those twelve command lines were "saved", did not exist outside the package at all.
  - Combined, that is the worst possible shape: the destructive half is real and the recovery half is not. Any move-style operation (delete here, save there) is therefore a data-loss bug on an unsigned package, not merely an unverifiable one. Do not write one until signing is proven end to end.
  - Do not generalise from a single observed case. An earlier note in this file claimed writes were fully contained, drawn from one entry whose delete had been masked by a stale container tombstone. It was wrong and it cost twelve real registry values.
  - **Closed on 2026-08-09: the move-style operation is now symmetric, measured from outside.** The startup domain does exactly the thing that was forbidden above — delete from `HKCU\...\Run`, save to `HKCU\Software\Winora\DisabledStartup` — and on the signed package both halves reach the real hive. Read from a separate unpackaged PowerShell: `DisabledStartup` holds thirteen command lines including `OneDrive` (`"C:\Program Files\Microsoft OneDrive\OneDrive.exe" /background`) and none of those thirteen names remains in live `Run`. So the recovery half is as real as the destructive half, which is precisely what was not true unsigned. The prohibition above stands for any *future* unsigned build; it is not a licence to skip this check, because the failure is invisible from inside the app.
- **A `Geometry` in a `ResourceDictionary` cannot be shared, and `PathIcon.Data` refuses one.** WinUI is not WPF: there are no freezables, and the assignment throws `E_INVALIDARG`. Measured on 2026-08-07 — the pane is built in the `MainWindow` constructor, so 0.2.4.0's predecessor installed and then would not open at all. Keep vector icons as path mini-language in `FluentIconCatalog` and parse a fresh instance per consumer through `IconGeometry.FromPathData`. Keep each path on one literal, however long: split across concatenated pieces, a dropped fragment is invisible in review and yields a subtly wrong shape.
- A catalog lookup that misses must not shrug. `FluentIconCatalog.TryGetGlyph` returning false left the bypass route with a blank space in the pane and nothing in any log, and it shipped that way. `IconCatalogTests` now fails when a route names an unknown icon or a pane item names none, and `MainWindow.IconFor` throws when the catalog holds path data the parser rejects — so an app that opens is proof the icon was built.
- **Contrast is measured, not judged.** `PaletteContrastTests` parses `Palette.xaml`, composites Winora's translucent sheet and cards over the Mica base, and holds every text brush to 4.5:1 against the *lightest* surface its theme can produce. The **hovered** card is the worst case and the one hand-checking misses: the faint tone read 3.89:1 on a resting card but 3.52:1 on a hovered one. Never reuse one grey across the dark and light themes — a single value cannot clear the floor against both a near-black and a near-white surface, and the test now refuses it.
- Two architecture tests keep the shell honest: every route key resolves to a real page, and every route is either shown in the shell or navigated to from code. They exist because three routes had rotted — two that nothing ever navigated to, and one whose page existed but had lost its only caller. Reading route files as text is deliberate; `PageCatalog` names WinUI types and cannot be loaded from a test host.
- A screen built over a data source nothing writes to is a feature that lies. `ActionJournal` was written, tested, registered — and never called, so the audit trail was empty on every machine for weeks. Wire the producer before building the reader.
- An unpackaged launch (`-p:WindowsPackageType=None`) is **not** a way to validate anything: on this machine it dies at `Application.Start` with `REGDB_E_CLASSNOTREG` before `App()` is even constructed, so composition never runs. Measured 2026-08-04. Install the signed package and launch that.
- **Launch the app after any change to dependency registration, and do not call the work done until it opens.** Composition is validated at startup (`ValidateOnBuild`), so an unresolvable dependency is fatal there — and the process ends before a window exists. On 2026-08-04 that made the shortcut do nothing at all: no window, no message, nothing in the Windows event log, because `ChangeHistory` asked for the concrete `DurableOperationJournal` while only the interface was registered. The reason was in `diagnostics.log` the whole time, so **read that file first** when the app will not start; a startup message box now points at it. The unit tests cannot catch this — `Winora.App.Tests` does not reference the WinUI assembly — so launching is the check.
- Release ritual, now that shipping means a signed package. Bump `Version` in `Package.appxmanifest`, build with `/p:GenerateAppxPackageOnBuild=true /p:UapAppxPackageBuildMode=SideloadOnly /p:AppxBundle=Never`, sign with `signtool sign /fd SHA256 /sha1 0FC883E670D49EAF70996A0E0B2820E7AB1C8104`, copy to `%USERPROFILE%\WinoraSigning\Packages`, and have the owner run `Add-AppxPackage` alone from an elevated prompt — **no `Remove-AppxPackage`**, see below. The certificate `CN=Winora` is in `LocalMachine\TrustedPeople` and its private key in `CurrentUser\My`. Two dead ends already eliminated by experiment, so do not re-test them: the `0x80070005` install failure is **not** the restricted `unvirtualizedResources` capability (two probe packages differing only by that capability and `RegistryWriteVirtualization` failed identically), and not folder ACLs (`C:\Users\Public` failed too, as did `C:`; Controlled Folder Access was disabled).
- Winora's store is `%USERPROFILE%\Winora\State` and must never move back under `AppData`. A packaged app has `%LOCALAPPDATA%` redirected into its container, so the store used to live at `%LOCALAPPDATA%\Packages\<PFN>\LocalCache\Local\Winora` — which the uninstaller deletes. State that can reverse changes to Windows has to outlive the app that made them. Two tests pin this: one on the exact path, one on the requirement that it is outside `AppData`. The plan of 2026-07-30 had already flagged this risk in writing and it shipped anyway, which is the reason it is now a test and not a note.
- **Never tell anyone to run `Remove-AppxPackage` to update Winora.** It deletes that directory, and with it the journal, the plan archive and every backup — while the changes those backups exist to undo stay applied to Windows. Measured on 2026-08-04: after a remove-then-install cycle, `ShowTaskViewButton` was still `1` and the operation that set it no longer existed, so it could not be rolled back. Installing a **higher version** with plain `Add-AppxPackage` is an update and keeps app data. The remove step was only ever needed once, to get from a dev-mode registration to a real package install (`0x80073CFB`, "the current user has already installed an unpackaged version"). That deeper problem is now fixed: since 2026-08-04 the store lives at `%USERPROFILE%\Winora\State`, outside the package container, so an uninstall no longer takes the backups with it.
- The package's write-copy hive is **not** under `%LOCALAPPDATA%\Packages\<PFN>` — it is `%ProgramData%\Packages\<PFN>\<SID>\SystemAppData\Helium\Cache\*.dat`, mounted as a silo hive (see `HKLM\SYSTEM\CurrentControlSet\Control\hivelist`). It survives `Remove-AppxPackage` plus re-register, because the kernel keeps the hive mounted for the logon session and flushes it back over the recreated file. Stale overlay state therefore persists until sign-out or reboot, and an app reading it back will keep reporting a change that the rest of Windows cannot see.
- `SPI_SETUIEFFECTS` is the master switch for most of the visual-effects domain. While it is off, Windows accepts a write to a dependent setting, returns success, and leaves the value unchanged. Measured on 2026-08-02. An earlier note in this file blamed a `SPIF_SENDCHANGE` broadcast delay for the same symptom — that was a wrong diagnosis of this effect. Apply `UIEFFECTS` first when turning effects on and last when turning them off, and treat a dependent setting as unchangeable while it is off.
- The `UIEFFECTS` dependency is modelled in two places and needs both. The probe reports a dependent setting as not writable while the master switch is off **or unreadable** (`VisualEffectDependencies`), and a preset orders the master switch first when turning effects on and last when turning them off (`VisualEffectPresetOrder`). Only the probe half is not enough: without the ordering a preset reports "changed 0, failed 16", which is what a user actually saw. Gate only the effects Microsoft documents as governed by the flag — gating an independent setting is the mirror-image lie, refusing a change that would in fact have worked.
- The ViewModel boundary test scans file **text**, not just `using` directives, so it also catches a fully qualified reach into the platform layer. It therefore trips on the assembly name appearing in a comment. Reword the comment; do not loosen the rule to a `using`-only match, because qualified access is exactly the case worth catching.
- `Winora.App.Tests` deliberately does not reference `Winora.App`: the WinUI assembly's CsWinRT module initializer fails with `REGDB_E_CLASSNOTREG` in a plain xUnit host, even for a POCO. Presentation logic that needs covering goes in its own file with no WinUI or MVVM dependency and is linked in with `<Compile Include>`. Do not try to solve this with `InternalsVisibleTo` — the problem is assembly activation, not accessibility.
- `PartiallyAppliedRecoveryRequired` used to have no exit, and one operation landing there permanently blocked every future change on a real machine. Cause: seven places move an operation into it and none moved one out — the reconcilers accept only `Applying` and `RollingBack`, the single legal transition out is `RollbackPlanned`, and `RollbackAsync` took the ordinary lease, which `GlobalMutationLease` refuses while anything is incomplete. Fixed on 2026-08-03: `RollbackAsync` falls back to `TryAcquireRecoveryAsync(plan.ChangePlan.PlanId)` and validates the binding against that id with `isRecovery: true`. The guard is not widened — the lease still grants recovery ownership only when exactly one operation is incomplete and the caller names it — and two tests pin both halves.
- A test fake that is more permissive than the thing it stands for hides exactly this class of bug. `InMemoryMutationLease` did not model the incomplete-operation refusal at all, so the deadlock was invisible to the whole Core suite until it happened to a user. When a fake stands in for something with a hard rule, encode the rule.
- Do not add another write into `PartiallyAppliedRecoveryRequired` without checking the way out still works.
- Verify every new mutation mechanism from **outside** the app, in a separate unpackaged process, before calling it done. Independent verification inside Winora cannot detect a container that redirects the write and serves it back: MSIX registry virtualization did exactly that to the taskbar domain, and every layer reported success while the real user hive was untouched. `windows.registryWriteVirtualization` is disabled in the manifest for this reason — re-check it after any manifest change.
- Temporary-file cleanup deletes permanently and bypasses the Recycle Bin, by explicit product decision: a cleaner that leaves the bytes on disk has freed nothing. The screen states this before the user acts and reports what a running process kept hold of. Everywhere else, never overstate `RollbackCapability` to make a feature look safer.
- Prefer a file mechanism over a registry one while the package is unsigned — it is the difference between a domain that works today and one that cannot be trusted at all. Cursors (`SetSystemCursor`), sounds, shortcut icons (`IShellLink::SetIconLocation`) and power plans (`PowerSetActiveScheme`) all bypass the virtualization problem for this reason, and all four were measured before being promised.
- Icon scope, measured on 2026-08-04 and settled: a pinned taskbar button is a real `.lnk` under `%AppData%\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar`, so its icon is changeable through the documented shell link interface. The tray network and volume glyphs and the taskbar clock font are **not** — Explorer draws them from resources inside signed system binaries, and the only route is patching those files. The Icons screen says so on the page rather than silently omitting them. Do not "find a way": that way is resource patching.
- Never judge a rendered cursor or icon by the alpha bytes of a single `DrawIconEx` pass. A cursor stored in the older mask-and-colour format has no alpha of its own, and `DrawIconEx` composites it with raster operations that leave the DIB's alpha bytes at zero — so a perfectly good cursor reads as fully transparent and gets reported as "no preview". Measured on a real pack whose every frame came back empty while the handle loaded and drew fine. `IconRasterizer` draws over black and over white and derives alpha from the difference; the black pass is already the premultiplied colour a bitmap wants, and the one path covers both cursor formats with no format sniffing.
- Cursor role tokens are matched by substring, first match wins, so prefer the **stem**: `work` covers `work` and `working`, `vert` covers `vert` and `vertical`, `unavail` covers the correct spelling and the common `unavailiable` misspelling. A pack whose normal-select file was called `default` matched nothing, which is the worst shape of failure here — the pack listed roles, showed no preview, and applying it changed nothing at all.
- The icons module was built and then removed on 2026-08-04 at the owner's request: what they wanted was tray, clock font and Start button, which are not changeable, and shortcut icons for ordinary apps were not wanted. Do not rebuild it without being asked.
- Keep user-facing text in `.resw` resources, preserve keyboard/High Contrast/200% support, and do not add inert controls.
- A performance screen must offer only what it can measure or documentedly change. Service shutdowns, `Win32PrioritySeparation` and registry "tweaks" are out of scope by specification, and the honest content is live figures plus the power plan.

## Build

- Use .NET SDK 10.0.203, C# 14, `net10.0-windows10.0.26100.0`, Windows App SDK 2.2.0, and x64.
- Do not raise the `Microsoft.WindowsAppSDK` pin without first confirming a matching Dynamic Dependency Lifetime Manager package is installed. Unpackaged launches resolve the framework through the DDLM for their exact version; a 2.3.x pin on a machine that only has `DDLM.2.2.0.0` produces a process that starts and exits with no window, no log, and no managed exception.
- The unpackaged loop (`-p:WindowsPackageType=None`) and the packaged layout share `bin\x64\<Config>\`, and `Add-AppxPackage -Register` points at that directory. Rebuilding one flavour silently corrupts a registration made from the other; always clean between them.
- Run focused tests while developing, then build `Winora.sln` with MSBuild 18 in both Debug and Release before a release.
- Do not commit generated output, certificates, packages, `.superpowers/` scratch files, or secrets.
